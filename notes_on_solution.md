# Notes on solution

## Changes

I've explored the idea of generating all the SQL necessary for rollups (as I've manually done in the branch `rollup-user-events`) in a declarative approach.

To get this done I've built a toy CLI tool in Python I've named `rollup-generator`. The tool reads an entity definition in JSON format which specifies:
* The events for an entity.
* A description of the rollup target table.
* How each event alters the target table.

From this definition, a SQL migration file is generated, which includes all the DDL, functions and triggers to replicate the pattern I applied in the branch `rollup-user-events`. The output can be used as a migration in `lana`.

## Running

We can use the `withdrawal` entity as an example to see how the workflow for this approach works. I've left a ready to use config file named `withdrawal_entity_definition.json` on the repo root.

I'll assume you have Python 3 and Poetry installed.

Prepare to use the tool:

```bash

cd rollup_generator
poetry install
poetry shell

```

Check it installed properly by running a smoke test:

```bash
rollup-generator smoke-test
```

Now you can check if the withdrawal's file I've supplied is OK:

```bash
rollup-generator validate-entity-definition ../withdrawal_entity_definition.json
```

Finally, you can move on to actually generating the SQL migration contents. Output goes to stdout, so we pipe to a file.

```bash
rollup-generator generate-entity-migration ../withdrawal_entity_definition.json > ../withdrawal_rollup.sql
```

Since `lana` already has a `core_withdrawal` table defined, we will run into a name conflict if we just add this as a migration. Let's run a tiny rename to avoid the conflict for the purpose of this demo:

```bash
cd .. 
sed -i 's/\bcore_withdrawals\b/pablos_core_withdrawals/g' withdrawal_rollup.sql
```

The work is done with the toy tool. Now we can go and check if our autogenerated SQL works.

We need to add the SQL file to our migrations.

```bash
nix develop

cd lana/app

cargo sqlx migrate add withdrawals_migration

cat ../../withdrawal_rollup.sql > "$(find migrations -type f -name '*withdrawals_migration*' | head -n 1)"
```

On two different terminals, get the dependencies running and run the `customer.bats` test to generate some withdrawal events.

```bash
nix develop
make reset-deps run-server
```

```bash
nix develop
bats -t bats/customer.bats
```

If all is well, the autogenerated rollup target table will now hold the latest state of the withdrawals created by the tests. I haven't created any tests for this, but you can simply peek at the contents with:

```bash
psql postgres://user:password@localhost:5433/pg -c "\x on" -c "select * from pablos_core_withdrawals;"
```

## Changes

Well, I rolled the Python CLI app and added the sample JSON for the withdrawal entity. Everything else in the repo remains unchanged.

The CLI app is anything but production grade, is heavily incomplete, and I don't think creating and adding a new dependency on a new language is the right way for this problem. My intention has only been to toy fast with the idea of generating SQL from a declarative file and showcase how it could be used with another entity with a tiny example.

Happy to discuss further in our call. I didn't put much effort into documenting the small app since it's a throwaway.

## Improvements and where to go from here

Should we want to take things further, I would look into:

* Deciding where and how do we want to declare entities, events and their rollup relationships. 
* Explore what's the best tooling to generate the SQL migrations that fits with the repo and team. I guess doing it directly in Rust within the existing codebase (pretty much continuing with what you have started on `lana/entity-rollups`) would be a wiser choice.

A few areas that I thing are uncertain and would need a lot of discussion:
* This approach only allows for very simple this-event-causes-this-rollup relationships before complexity grows a lot. Again, I would question if this is the right path given the risk of either (1) falling short and having a mini-framework that is too constrained feature wise or (2) trying to build something abstract enough and falling into a black hole of effort and complexity in the process.
* The challenge and solutions are very focused on the idea of rolling up events into a projection that holds the last event of the entity. But we will also face the need to create projections that are not simple representations of entities and their current state, but rather more sophisticated abstractions (e.g. the simple withdrawals table vs a projection that holds all the expected net cashflows per day for the next 90 days). Given the point I mention before, how would we build this kind of non-entity-projections? Would we not use our tool? Is it a good idea to have some projections be auto-generated and others be handcrafted?
